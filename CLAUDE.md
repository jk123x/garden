# Garden Catalogue

Personal garden care app for tracking plants and seasonal tasks. Melbourne, Zone 10b.

**What this project is for (Jay, July 2026):** quick-reference guides. Jay grabs spare moments in the garden and wants to glance at a page and instantly know the next task and how to do it. Every page, card and nextAction should be written for that glance — task first, instructions inline, no context-hunting. Seamless is the bar.

## Stack

- Astro 6 + Tailwind CSS v4 (using `@theme` in global.css, no tailwind.config)
- Static site, deploys to Vercel
- Dev server: port 4325
- Tests: vitest (`npm test`). `src/lib/schedule.test.ts` covers the date-placement logic. Add tests when touching schedule.ts
- **Images live in `src/images/`** (plants/, winter-2026/, field/), NOT public/. YAML keeps the old `/images/...` paths; `resolveImage()` in `src/lib/images.ts` maps them to imports and `<Photo>` (src/components/Photo.astro) renders resized webp with srcset. Never use a bare `<img src="/images/...">`. Gallery "open full size" links use a 1600px jpg via `getImage`. `npm run build` runs `scripts/prune-unreferenced-assets.mjs` afterwards to drop the raw originals from dist (348MB → ~160MB). First build processes ~750 variants (~25s); later builds hit the cache

## Key patterns

- **`src/lib/schedule.ts` is the single source of truth for date placement** (placeTask, taskChip, deadlineKey, attentionChip, isWaiting, windowEnd). index.astro imports it in BOTH the frontmatter (first paint) and the client `<script>` (re-placement against the real date). Never duplicate that logic inline again
- Indoor/outdoor toggle persisted in localStorage, filters via `data-indoor` attributes (style.display)
- Plant type filters on `/plants` use `data-type` + `data-typeHidden`; health filters use `data-health` + `data-healthHidden`
- Category colors + health status colors/labels/dots in `src/lib/utils.ts` as Tailwind class strings
- `SEASONAL_CONTEXT` in utils.ts — Melbourne seasonal notes for all 12 months (currently not rendered anywhere)
- `getPlantsNeedingAttention()` returns `{ attention, waiting, later, unassessed }`
- `getTasksForMonth()` is the core data helper for the calendar
- Components: `Photo.astro` (optimised image, class passthrough), `HealthBadge.astro`. AttentionCard was unused and removed

## Dashboard rules

- The dashboard "To do" section is **data-driven** — pulled from plants with `urgency` set, displaying `nextAction`. Do not add hardcoded HTML lists to `index.astro`. To add a to-do item, edit the relevant plant YAML.
- **High-Impact Weeding is a PERMANENT 'Whenever you're passing' item** (Jay, 8 Sept 2026): never clear its `urgency: later` / nextAction when he reports a weeding pass. Log the pass, keep the standing job. It's his filler for an empty or dull to-do list
- **The organising principle is actionability, not importance** (Jay, 21 Aug 2026): the box answers "what can I do right now with spare garden time." Two visible states: **Do now** (actionable today) and **Whenever you're passing**; date-blocked work is hidden until its date (no Waiting list) (doable any time, low priority — the `later` tier).
- **Date windows:** optional `readyFrom` / `dueBy` (YYYY-MM-DD) on the plant. An urgency item with a future `readyFrom` is HIDDEN until that date and **auto-appears in "Do now" on the day — client-side JS in index.astro re-sorts against the real current date on every page load**, so no manual re-tagging and no stale build-time splits. `dueBy` shows a "by 27 Aug" chip that flips red ("was due") once passed. Any date-gated task (spray windows, treatment intervals, "check in early Sept") should get `readyFrom` + `urgency: today/week` — do NOT park date-gated work in `later`, and do NOT write dates only into nextAction prose.
- **A task with a date in it gets `day:`, never a date in the prose** (Jay, 8 Sept 2026, twice, angrily): "check in 3 weeks", "late Sept", "from the 25th" = `months: [9]` + `day: 28`. The schedule hides it until the 28th and surfaces it in Do now that day. A follow-up check after any job (dieback watch, spray interval, regrowth check) is ALWAYS a `day`-gated task row or a `readyFrom` urgency item. If it lands in Do now the day it's written, it's wrong. Scan before finishing any session: `node -e` js-yaml for tasks matching /late|mid|early|in \d weeks|\d{1,2} (Sep|Oct|...)/ with no `day` and no `completed`
- **nextAction contains ONLY the immediate job** (Jay, 5 Sept 2026: "why put aerate on my to do list if it's not til october? our whole thing is using the calendar"). Future work never rides along as prose in a do-now card. ## Watering and irrigation

The garden runs **garden-wide drip irrigation** that's switched off through autumn and winter (rain handles it) and back on for spring/summer. Do NOT add per-plant "reduce watering", "less water in winter", or "minimal watering" tasks — they're noise. Watering at the system level is Jay's call, not a per-plant decision.

Per-plant watering tasks should only exist for: (a) new plantings before they're hooked into drip, (b) plants with genuinely different water needs (succulents, drought-natives in pots), or (c) deep-watering during specific heat events.

## Logging field work

Plant YAMLs have a `log` field — array of `{ date, entry, category? }`. Use it for dated, one-off observations and work (weeding, pest sightings, repairs, infestations). Distinct from `tasks` (recurring monthly template) and `notes` (durable description). When Jay reports field work, append to the relevant plant's `log`, update `lastAssessed`, and refresh the `health` line if the state changed.
